SLIDE 2: PROBLEM STATEMENT & SYSTEM OBJECTIVES
-----------------------------------------------------------------------------
* The Challenge:
  - Institutional student housing involves multiple disjointed workflows: 
    room allocation, fee billing, complaint tracking, inventory control, out-passes, 
    mess menus, and visitor logs.
  - Using manual logbooks or isolated local spreadsheets leads to redundancy,
    data inconsistency, lack of transactional safety, and poor multi-user concurrency.
* System Objectives:
  - Create a unified, centralized transactional relational database (PostgreSQL).
  - Implement Role-Based Access Control (RBAC) at the application and schema layers.
  - Enforce referential integrity to prevent orphaned entries (e.g., student details
    remaining after account deletion).
  - Utilize database-level triggers to guarantee real-time synchronization of counters
    (such as room vacancy capacity) and ledger status.
  - Provide a high-performance system through optimized database indexing and views.

SLIDE 3: SYSTEM ARCHITECTURE & DATA FLOW
-----------------------------------------------------------------------------
* Technical Stack:
  - Frontend: Responsive Client UI built using HTML5, Vanilla CSS3 (custom glassmorphism design),
    and Vanilla JavaScript, optimized via Vite.
  - Backend: RESTful API powered by Python 3.12 and FastAPI. Pydantic is used for request 
    validation and data serialization.
  - ORM Layer: SQLAlchemy is utilized as the Object-Relational Mapper, executing transaction blocks 
    and mapping PostgreSQL rows to Python objects.
  - Database System: PostgreSQL 16+ hosted on Azure Database for PostgreSQL Flexible Server (Cloud DBaaS).
* Client-Server-DB Data Flow:
  1. Client sends an HTTP request with JWT authentication headers.
  2. FastAPI Backend interceptor verifies credentials, opens an active database session pool.
  3. SQL Queries / Stored Procedures are dispatched to PostgreSQL via the Psycopg2 database driver.
  4. PostgreSQL executes the transaction, fires triggers, updates indexes, and returns the result.
  5. Connection is returned to the connection pool, and backend sends JSON responses back to the client.

SLIDE 4: ENTITY-RELATIONSHIP (ER) DESIGN & RELATIONSHIPS
-----------------------------------------------------------------------------
* Core Entity Sets:
  - Users, Students, Wardens, Hostels, Rooms, Fee Structures, Invoices (Student Fees), 
    Complaints, Leaves, Visitors, Room Change Requests, and Inventory.
* Primary Relationship Cardinalities:
  - Hostel to Room (1 : N) - A hostel contains multiple rooms; a room belongs to one hostel.
  - Student to Room Allocation (1 : N) - A student can have multiple historical allocations, 
    but only one active room allocation at any time.
  - Student to Student Fee (1 : N) - A student can have multiple outstanding fee invoices over terms.
  - Student Fee to Payment (1 : N) - A single fee invoice can have multiple partial payments.
  - Student to Complaint (1 : N) - A student can file multiple maintenance complaints.
  - Warden to Complaint (1 : N) - A warden is assigned to manage multiple student complaints.
  - Inventory to Inventory Transaction (1 : N) - An inventory item logs multiple transactions (Add/Remove).
* Referential Integrity Mappings:
  - ON DELETE CASCADE: When a record in the parent table (`users`, `student`, `hostel`, `room`) is deleted,
    associated dependent records in child tables (`student`, `room_allocation`, `payment`, etc.) are
    automatically purged to prevent database fragmentation.
  - ON DELETE SET NULL: Used when deleting a warden; the complaints assigned to them or hostel managed
    by them will have their reference set to NULL instead of breaking the record.
  - ON DELETE RESTRICT: Prevents deletion of a parent record if children exist. E.g., a `fee_structure`
    cannot be deleted if a student is already billed under that structure.

SLIDE 5: DATA DICTIONARY & SCHEMA OVERVIEW (PART 1 - AUTH & GENERAL)
-----------------------------------------------------------------------------
The database consists of 19 normalized tables structured as follows:

1. users (Authentication & RBAC)
   - user_id (INT, PK, SERIAL)
   - username (VARCHAR(50), UNIQUE, NOT NULL)
   - password_hash (VARCHAR(255), NOT NULL)
   - role (VARCHAR(20), CHECK role IN ('ADMIN', 'WARDEN', 'STUDENT', 'ACCOUNTANT'))
   - created_at (TIMESTAMP, DEFAULT current)

2. warden (Staff Details)
   - warden_id (INT, PK, SERIAL)
   - user_id (INT, FK -> users(user_id) ON DELETE CASCADE)
   - name (VARCHAR(100), NOT NULL)
   - email (VARCHAR(100), UNIQUE, NOT NULL)
   - phone (VARCHAR(15))

3. hostel (Building Configuration)
   - hostel_id (INT, PK, SERIAL)
   - hostel_name (VARCHAR(100), UNIQUE, NOT NULL)
   - hostel_type (VARCHAR(20), CHECK hostel_type IN ('BOYS', 'GIRLS', 'COED'))
   - capacity (INT, NOT NULL)
   - warden_id (INT, FK -> warden(warden_id) ON DELETE SET NULL)

4. room (Room Slots)
   - room_id (INT, PK, SERIAL)
   - hostel_id (INT, FK -> hostel(hostel_id) ON DELETE CASCADE)
   - room_number (VARCHAR(20), NOT NULL)
   - floor (INT, NOT NULL)
   - room_type (VARCHAR(30), CHECK room_type IN ('SINGLE', 'DOUBLE', 'TRIPLE', 'COMMON'))
   - capacity (INT, NOT NULL)
   - occupied_count (INT, DEFAULT 0, CHECK occupied_count <= capacity)
   - status (VARCHAR(20), DEFAULT 'AVAILABLE', CHECK status IN ('AVAILABLE', 'FULL', 'MAINTENANCE'))
   * Composite Unique Constraint: UNIQUE(hostel_id, room_number)

5. student (Student Enrolment)
   - student_id (INT, PK, SERIAL)
   - user_id (INT, FK -> users(user_id) ON DELETE CASCADE)
   - roll_no (VARCHAR(20), UNIQUE, NOT NULL)
   - name (VARCHAR(100), NOT NULL)
   - email (VARCHAR(100), UNIQUE, NOT NULL)
   - phone (VARCHAR(15))
   - department (VARCHAR(100))
   - year (INT)
   - gender (VARCHAR(20))
   - date_of_birth (DATE)
   - status (VARCHAR(20), DEFAULT 'ACTIVE', CHECK status IN ('ACTIVE', 'GRADUATED', 'SUSPENDED', 'LEFT'))

6. room_allocation (Room Assignments)
   - allocation_id (INT, PK, SERIAL)
   - student_id (INT, FK -> student(student_id) ON DELETE CASCADE)
   - room_id (INT, FK -> room(room_id) ON DELETE CASCADE)
   - allocation_date (DATE, DEFAULT current)
   - vacated_date (DATE)
   - status (VARCHAR(20), CHECK status IN ('ACTIVE', 'COMPLETED', 'CANCELLED'))

SLIDE 8: DATA ABSTRACTION: DATABASE VIEWS
-----------------------------------------------------------------------------
To simplify complex query execution for the application tier, four optimized views are defined:

1. available_rooms:
   - Purpose: Lists all rooms that are open for new allocations.
   - Logic: Performs an Inner Join of `room` and `hostel`, filtering out rooms where status != 'AVAILABLE'
     or where occupied_count has reached its capacity limit.

2. hostel_occupancy:
   - Purpose: Computes hostel building utilization metrics.
   - Logic: Aggregates room capacity and occupancy across hostels using a Left Join, and performs 
     real-time percentage calculations (with division-by-zero protection via COALESCE).

3. pending_fees (Defaulters list):
   - Purpose: Identifies students with unpaid invoices.
   - Logic: Joins `student` and `student_fee`, computing (amount_due - amount_paid) and filtering rows 
     where the balance outstanding is greater than 0.

4. complaint_summary:
   - Purpose: High-level analytics of infrastructure tickets.
   - Logic: Performs a GROUP BY aggregate count of ticket rows categorized by priority, classification, 
     and status.

SLIDE 9: QUERY PERFORMANCE & INDEXING STRATEGY
-----------------------------------------------------------------------------
To prevent slow sequential tables scans on millions of transactions, key indexes were placed:

* idx_student_rollno: B-Tree Index on `student(roll_no)`. Speeds up student verification during login
  and check-in.
* idx_room_hostel: Index on `room(hostel_id)`. Optimizes Room list lookup operations for specific blocks.
* idx_room_status: Index on `room(status)`. Accelerates search queries looking for vacant rooms.
* idx_allocation_student: Partial Index on `room_allocation(student_id) WHERE status = 'ACTIVE'`.
  Drastically reduces lookup times when searching for a student's currently active room allocation.
* idx_payment_student & idx_attendance_date: Speeds up financial ledger queries and attendance reports.

SLIDE 10: TRIGGER-BASED AUTOMATION (SERVER-SIDE INTELLIGENCE)
-----------------------------------------------------------------------------
Data consistency is enforced at the database layer using PL/pgSQL database triggers:

1. Room Occupancy Sync (`trg_update_room_occupancy`):
   - Trigger Event: AFTER INSERT, UPDATE, or DELETE on `room_allocation`.
   - Logic: Automatically increments `occupied_count` in the `room` table for new active assignments,
     decrements it when a student vacates, and shifts the room's status domain between 'FULL' and
     'AVAILABLE' dynamically based on capacity checks.

2. Automated Invoice Ledger Updates (`trg_update_payment_status`):
   - Trigger Event: AFTER INSERT or UPDATE on `payment`.
   - Logic: When a successful payment transaction occurs, this trigger automatically aggregates all 
     historic successful payments for the invoice, updates the total `amount_paid` inside `student_fee`,
     and moves the status state machine ('PAID', 'PARTIAL', or 'PENDING') accordingly.

3. Complaint Resolution Clock (`trg_complaint_resolution`):
   - Trigger Event: BEFORE UPDATE on `complaint`.
   - Logic: Automatically marks the `resolved_at` timestamp with the database current time if the status
     transitions to 'RESOLVED', eliminating client-side clock drift.

SLIDE 11: TRANSACTION MANAGEMENT & PROCEDURES (ACID PROPERTIES)
-----------------------------------------------------------------------------
To prevent data anomalies, stored functions run processes within transaction scopes:

* Stored Function: `allocate_room(p_student_id, p_room_id)`
  - Encapsulates room booking validation and insertion in an atomic block.
  - Step 1: Confirms the student's status is 'ACTIVE'.
  - Step 2: Verifies the student does not already possess an active allocation.
  - Step 3: Verifies the destination room status is 'AVAILABLE' and has open beds.
  - Step 4: Inserts the allocation. (This triggers `trg_update_room_occupancy` atomically).
  - Transaction Isolation: If any step fails, the entire transaction is rolled back, 
    preventing double-booking anomalies (Atomicity & Isolation).

* Stored Function: `vacate_room(p_student_id)`
  - Finds the active allocation for the student and transitions the status to 'COMPLETED',
    setting the vacated date to the current date. Atomically updates the occupied bed counts.

SLIDE 12: CONCLUSION & DBMS CORE METRICS
-----------------------------------------------------------------------------
* Academic Takeaways from ResiKeep:
  - Enforced Referential Integrity via strict Foreign Key Constraints (Cascade & Restrict actions).
  - Maintained 3NF normalization throughout the 19 tables, eliminating modification anomalies.
  - Demonstrated ACID properties (Atomicity, Consistency, Isolation, Durability) using Stored
    Procedures and row locks during transactions.
  - Offloaded operational business logic from FastAPI compute application server down to the database
    engine using triggers and procedures, ensuring database-level data sanitization.
